# Shipping Riposte

Config for deploys is in the repo; the deploys themselves need your Vercel /
Apple Developer / App Store Connect accounts — none of which this assistant
has access to. Everything below marked **(you)** has to happen in those
dashboards or on a Mac; everything else is already done in the repo.

## Environment variables

Never commit secrets. Set these in the respective dashboards.

| App | Var | Where |
|-----|-----|-------|
| `apps/admin` | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | Vercel project env |
| `apps/mobile` | `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` | `.env` locally; Xcode Cloud workflow env vars for CI builds |
| Edge Functions | `XMONEY_SECRET_KEY`, `XMONEY_SITE_ID` (+ optional `XMONEY_CUSTOMER_COUNTRY`, `XMONEY_APP_RETURN_URL`, `XMONEY_FUNCTIONS_BASE_URL`) | Supabase → Edge Functions → Secrets |

`apps/mobile/.env.example` documents the mobile vars. The xMoney secret key is
deliberately *not* an `EXPO_PUBLIC_*` var — those are compiled into the app
binary and readable by anyone who downloads it. See `docs/xmoney.md`.

## Admin web → Vercel (private, custom domain)

`vercel.json` (repo root) builds the admin workspace and serves its output:

- Build command: `npm run build` → `npm --workspace @riposte/admin run build`
- Output: `apps/admin/dist`
- Install: `npm install` (workspace-aware, resolves `@riposte/core`)

The app itself keeps you out unless you're in the `admins` Supabase table —
`AdminGate` (`apps/admin/src/AdminGate.jsx`) requires Google sign-in and
checks `resolveUserRole`. On top of that, the site is kept off search engines
(`apps/admin/public/robots.txt` disallows everything, `index.html` sets
`<meta name="robots" content="noindex, nofollow">`) and is meant to live on
an unlisted custom domain rather than a public/marketing one.

Steps:
1. Import the repo into Vercel; keep **Root Directory = repo root** (the
   `vercel.json` handles the monorepo build).
2. Add `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`.
3. **(you)** Vercel dashboard → project → Settings → Domains → add your
   private subdomain (e.g. `admin.sportriposta.ro`) → add the CNAME/A record
   it gives you at your DNS provider.
4. Deploy. The SPA rewrite serves `index.html` for all routes.

Note: Vercel's free "Standard Protection" (a real sign-in gate on top of the
app) only covers the default `*.vercel.app` URL — it does **not** extend to
custom domains on the free tier. Custom-domain protection requires Pro +
Advanced Deployment Protection. The `AdminGate` + noindex + unlisted-domain
combination above is the free-tier equivalent for a custom domain.

## Mobile → Xcode Cloud → TestFlight

Primary CI/CD is **Xcode Cloud**, triggered on every push to `main`, auto-
distributing to TestFlight Internal Testing. `apps/mobile/eas.json` is kept
around only for optional ad hoc dev-client builds (`eas build --profile
development`) — it is not part of the shipping path.

`app.json` sets `scheme: "riposte"` and bundle id `ro.sportriposta.riposte`.
`apps/mobile/ios/` is the generated native Xcode project (via `expo
prebuild`), committed to the repo — Xcode Cloud requires a physical
`.xcodeproj`/`.xcworkspace` to configure a workflow against; the fully
managed EAS-only workflow can't do this. **If you change anything
`app.json`-driven** (icons, permissions, bundle id, adding a native module),
regenerate it:
```sh
cd apps/mobile
npx expo prebuild --platform ios --clean
```
then commit the result. `apps/mobile/ios/.gitignore` (generated by prebuild)
already excludes `Pods/` and `build/` — those regenerate on every CI run via
`pod install`, no need to commit them. Everything else under `ios/`,
including `Podfile.lock`, is committed.

`apps/mobile/ios/ci_scripts/`:
- `ci_post_clone.sh` — Xcode Cloud's Mac images don't ship Node.js by
  default; this installs it via Homebrew (version pinned by
  `apps/mobile/.nvmrc`), then runs `npm ci` at the monorepo root (resolves
  `@riposte/core`) and `pod install` in `ios/`.
- `ci_pre_xcodebuild.sh` — writes `apps/mobile/.env` from the Xcode Cloud
  workflow's environment variables, so Expo's `.env` loader picks up
  `EXPO_PUBLIC_SUPABASE_URL`/`_ANON_KEY` regardless of whether Xcode's build
  phases inherit custom-script env vars directly.

### **(you)** One-time setup

1. **Apple Developer Portal** → Certificates, Identifiers & Profiles →
   Identifiers → **+** → App IDs → App. Bundle ID **Explicit**:
   `ro.sportriposta.riposte`. **Check "Push Notifications" under
   Capabilities** — required now: `expo-notifications` is already a plugin
   in `app.json`, so `expo prebuild` already added the `aps-environment`
   entitlement (`apps/mobile/ios/Riposte/Riposte.entitlements`) even though
   push isn't wired up yet. Skipping this makes the first Xcode Cloud archive
   fail to sign.
2. **App Store Connect** → Apps → **+** → New App. iOS. Name `Riposte` (check
   App Store name availability first). Bundle ID: select
   `ro.sportriposta.riposte` (only appears once step 1 is done).
3. On a Mac: `cd apps/mobile/ios && pod install` once, to generate
   `Riposte.xcworkspace` (not committed as a build artifact of prebuild
   itself — it's produced by CocoaPods, which needs to run locally at least
   once before you can open the workspace in Xcode).
4. Open `Riposte.xcworkspace` in Xcode → Product menu → **Xcode Cloud** →
   Create Workflow → sign in with the Developer-Program Apple ID → authorize
   the Xcode Cloud GitHub App for this repo → select the `Riposte` scheme.
5. Configure the workflow:
   - **Start Condition**: Branch Changes → `main`, auto-start on push.
   - **Environment**: pin an explicit Xcode version (not "Latest Release") —
     safer given `newArchEnabled: true`'s stricter CocoaPods/codegen needs.
   - **Actions**: Archive.
   - **Post-Actions**: TestFlight (Internal Testing), auto-distribute.
   - **Environment Variables**: `EXPO_PUBLIC_SUPABASE_URL`,
     `EXPO_PUBLIC_SUPABASE_ANON_KEY` (mark the key Secret if you want it
     masked in logs).
6. Save. Next push to `main` triggers a build, or trigger manually to
   validate now. Watch the log (Xcode Report Navigator, or App Store
   Connect → Xcode Cloud) for `ci_post_clone.sh` succeeding, a successful
   Archive, then a TestFlight delivery.

Google OAuth: add the `riposte://auth/callback` redirect (and the Supabase
callback URL) to the Google OAuth client and to Supabase Auth → URL config.

## Push notifications

`expo-notifications` is installed and configured (`app.json` plugin, and —
see above — it already put the `aps-environment` entitlement in the iOS
project) with a `registerForPushNotifications()` scaffold in
`src/lib/notifications.ts`. Not wired into the app yet — a later phase stores
the token per member and sends lesson reminders / booking confirmations.

## Native project provenance

`apps/mobile/ios/` is generated by `expo prebuild`, not hand-written, and not
a leftover from the old Capacitor setup — Capacitor itself (`@capacitor/*`,
`capacitor.config.ts`, `scripts/ios-setup.sh`) is fully retired. The mobile
app is pure Expo; `ios/` exists only because Xcode Cloud requires a physical
native project to configure a workflow against.

## Security migration

Before real users: apply `supabase/migrations/add_rls_hardening.sql` and test
with scoped tokens (see `rewrite-plan.md` → Verification). Coaches/admins must
sign in once (or be linked manually) so their `user_id` populates.

## Card payments (xMoney)

`docs/xmoney.md` is the runbook: run `add_xmoney_payments.sql`, set the
function secrets above, deploy the three Edge Functions with `--no-verify-jwt`,
and point xMoney's notification URL at `…/functions/v1/xmoney-webhook`. Test
with an `sk_test_` key before switching to `sk_live_` — the key prefix alone
decides which xMoney environment the checkout posts to.
